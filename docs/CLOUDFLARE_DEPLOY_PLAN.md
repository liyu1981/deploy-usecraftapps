# Cloudflare Pages deploy plan: large WASM via byte-stitching

## Goal

Deploy this repository to **Cloudflare Pages (free tier)** without hitting the
**25 MB per-file limit**. Several apps ship a single `*_bg.wasm` above that
limit (up to ~77 MB). The plan follows the byte-stitching approach: split
oversized WASM at build time into <= 20 MB chunks, serve them as static
files, and reassemble them in the browser before instantiation.

No Cloudflare Functions, R2, or per-request logic is used, so there are no
Class A/B operation caps and no extra cost.

## Current state

- `prepare-public.sh` materialises Git LFS objects into `public/`.
- Most apps load one `*_bg.wasm` directly from `index.html`.
- `photocraft` already uses an upstream "parts" scheme
  (`app/parts.txt` + `app/*.part-*`, assembled by its boot module).
- `effectcraft` and `lightcraft` call `WebAssembly.compileStreaming(...)` and
  share the compiled module with workers.
- `filmcraft` passes a `URL` to `init`.
- Cloudflare-facing headers live in the root `_headers` (generated by
  `update-crafts.sh`) and `wrangler.toml`.

Files currently above the 25 MB limit are all `*_bg.wasm`:

## Strategy

0. **Keep the repository clean:** all Cloudflare-specific prepared output goes
   into the gitignored `workspace/` folder; source `public/` stays committed
   and untouched.
1. **Build-time split only oversized `*_bg.wasm`** into `<= 20 MB` chunks.
2. **Keep the original filename as a virtual URL** by intercepting `fetch`
   in a tiny bootstrap module: when the app requests `.../foo_bg.wasm`, the
   bootstrap fetches `.../foo_bg.wasm.manifest`, downloads the chunks, stitches
   them into one `ArrayBuffer`, and returns a `Response`. Existing app code
   (`init`, `compileStreaming`, `fetch`) keeps working unchanged.
3. **No per-app JS edits** beyond injecting the bootstrap script and removing
   stale WASM preload links.
4. **Update headers** so chunks are `application/octet-stream`, immutable, and
   manifests are `no-cache`.
5. **Leave `photocraft` on its native parts scheme** (already Cloudflare-safe).

## Phase 1 — Build-time splitting

Add a `prepare-cloudflare.sh` that builds into a gitignored output folder:

1. Runs `prepare-public.sh` (Git LFS materialisation) into `public/` — unchanged.
2. Copies `public/` to `workspace/public/` (the Cloudflare build output).
3. For every `workspace/public/**/*_bg.wasm` larger than the threshold (20 MiB):
   - Split with `split -b 20971520 -d -a 3 <file> <file>.`
     producing `<file>.000`, `<file>.001`, …
   - Write `<file>.manifest` containing one relative chunk filename per line.
   - Delete the original `*_bg.wasm`.
4. Copy a shared `stitch-bootstrap.js` to `workspace/public/stitch-bootstrap.js`.
5. Inject `<script type="module" src="/stitch-bootstrap.js"></script>` into
   each app `index.html` before its app module (or into the root shell where
   applicable).
6. Strip `<link rel="preload" ... application/wasm">` entries from
   `index.html` files, since the original WASM no longer exists.
7. Fail the build if any file in `workspace/public/` is still `> 25 MB`
   (`find workspace/public -type f -size +25M`).

Threshold and chunk size are intentionally below Cloudflare's 25 MB limit
with margin for filesystem/transport overhead.

## Phase 2 — Client-side reassembly (bootstrap)

`stitch-bootstrap.js` (served from `/`, no-cache) does:

- Save the original `fetch`.
- Replace `window.fetch` with a wrapper that:
  - Normalises the request URL.
  - If the pathname does **not** end in `_bg.wasm`, delegate to original
    `fetch`.
  - Otherwise try `fetch(<url>.manifest)`:
    - If 404, delegate to original `fetch` (small/unsplit WASM still present).
    - Otherwise read chunk names, fetch them sequentially in the first
      version, stitch into a single `Uint8Array`/`ArrayBuffer`, and return
      `new Response(buffer, { headers: { "Content-Type": "application/wasm" } })`.
- Keep `WebAssembly.compileStreaming` working: it receives the stitched
  `Response` and compiles it (the Response body is the stitched bytes).

Memory note: sequential fetch still holds chunk buffers plus the combined buffer
(~2x peak). For the largest app this is ~150 MB. If mobile/low-end memory
becomes a problem, switch the bootstrap to streaming concatenation or smaller
chunk size.

## Phase 3 — Cloudflare Pages configuration

### Dashboard / Wrangler

- **Build command:** `bash prepare-cloudflare.sh`
- **Build output directory:** `workspace/public` (derived, gitignored)
- **Framework preset:** None
- Keep `wrangler.toml` `pages_build_output_dir = "workspace/public"`.

### Headers (`_headers`)

Generated root `_headers` should include:

```
/*
  X-Content-Type-Options: nosniff

/*.wasm
  Content-Type: application/wasm

/*_bg.wasm.manifest
  Cache-Control: no-cache

/stitch-bootstrap.js
  Cache-Control: no-cache

/*_bg.wasm.*
  Content-Type: application/octet-stream
  Cache-Control: public, max-age=31536000, immutable

/*/app/*.part-*
  Content-Type: application/octet-stream
  Cache-Control: public, max-age=31536000, immutable

/*/app/parts.txt
  Cache-Control: no-cache
```

Chunks are immutable because their names embed the WASM content hash.
Manifests and the bootstrap are `no-cache` so updates propagate.

### Git LFS

Unchanged: Cloudflare build still runs LFS materialisation first. Split
artifacts are derived build outputs and are **not** committed.

## Phase 4 — Update flow integration

- `update-crafts.sh` continues to download upstream releases and rebuild
  `public/` (including per-app patches).
- After regeneration, `prepare-cloudflare.sh` (or CI) performs the split.
- `cron-update.sh` should call the Cloudflare prepare script before push, or
  Cloudflare Pages build should run it.
- Prefer doing the split in the **Cloudflare build**, not in the committed
  repo, so Git history stays small and upstream updates remain trivial.

## App-family considerations

| Family | Examples | Bootstrap impact |
|---|---|---|
| Simple wasm-bindgen | cadcraft, deckcraft, vectorcraft, wordcraft, figcraft, gridcraft, soundcraft, pdfcraft | `fetch` patch covers `init({ module_or_path: url })`. |
| Shared compiled module | effectcraft, lightcraft | `compileStreaming(fetch(url))` receives stitched Response; assign stitched module to the existing global. |
| Custom URL loader | filmcraft | `new URL(...)` becomes a fetch; bootstrap intercepts. |
| Native parts | photocraft | No change; already <= 25 MB. |

Service workers (`effectcraft` registers `sw.js`) may cache the original WASM
URL. Either bump the SW cache version or exclude `*_bg.wasm` / manifests /
chunks from precaching. Plan to test SW behaviour specifically.

## Risks and mitigations

- **Memory spike**: sequential stitching still holds chunk buffers plus the
  combined buffer (~2x WASM size). Mitigate with streaming/concatenation or
  smaller chunk size if needed.
- **First-paint delay**: no streaming compilation; all chunks must download
  first. Acceptable trade-off for free tier.
- **Integrity (SRI)**: preload integrity hashes for WASM become invalid;
  strip them at build time.
- **Service worker cache**: update cache keys or skip WASM precache.
- **Upstream changes**: if an app changes its loader pattern, the fetch
  interceptor may need updating; it is centralised in one file.

## Out of scope

- Committing split chunks to Git.
- Changing upstream build pipelines.
- Using R2 or Cloudflare Functions.
- Modifying app source code.
